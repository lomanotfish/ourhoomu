# ADR-0002: ใช้ Neon ตามคำสั่งผู้ใช้

Date: 2026-10-12
Status: Accepted สำหรับ database/project setup และ private slip storage เท่านั้น
Supersedes: [ADR-0001](0001-stack.md) ส่วน Supabase backend/database

ผู้ใช้เลือก Neon database และให้รัน npm global install/login, neon skills -y, neon mcp -y, link lucky-bar-14515304 branch production, config init, เขียน neon.ts ตามตัวอย่าง และ neon deploy จึงมี authorization สำหรับ infrastructure setup นี้โดยไม่ต้องถามซ้ำ General app implementation ยังรอ full design approval

## คำตัดสิน

- Database: Neon PostgreSQL โปรเจกต์ ourhoomu; production branch br-shy-frog-b30wrl6l; region aws-ap-southeast-1; server รายงาน PostgreSQL 18
- Files: Neon Object Storage bucket slip แบบ private ตาม neon.ts ที่ผู้ใช้ระบุ เก็บ preview.buckets ตามคำขอตรงตัว แม้ CLI 8.3.5 แจ้งว่าย้ายไป top-level buckets ได้แล้ว
- Backend/frontend folder ยังคง ourhoomu-api และ ourhoomu-front; Expo/React Native เป็นข้อเสนอเดิม
- งานนี้ไม่ได้เปิด Auth/Functions/Data API เพิ่มหรือสร้าง schema บิล/เวร Remote status พบ Neon Auth เปิดอยู่แล้ว ต้องตรวจ integration กับ Google/Apple ก่อนใช้ ไม่ถือว่าการตั้งค่า login ของแอปเสร็จแล้ว ต้องตรึง API hosting, session verification, actor identity, database grants/RLS และ transaction contract ก่อนพัฒนา ไม่สมมติ Supabase auth.uid()/service role/RPC transport
- Slip private bucket เป็น infrastructure permission เท่านั้น ยังไม่มี app-level uploader/recipient access control ต้องทำ authenticated API stream และ fresh membership checks ตาม domain/API contract
- Native Google/Apple login ผ่าน API, exact money/งวด, cash creator confirmation, chore modes และ retention ไม่เปลี่ยนตามการเปลี่ยน provider

## ผลกระทบ

ถอนคำสั่ง Supabase CLI/local containers/Deno-specific scaffolding ออกจาก active plan ใช้ SQL migrations ภายใต้ ourhoomu-api หลังตรึง backend runtime ใหม่ ไม่ย้ายข้อมูลจริงเพราะ repo ยังไม่มี implementation; ไม่รับรองว่าทุก free-tier quota หรือ retention behavior เดิมใช้กับ Neon ได้

ตรวจ plan/usage/history retention ของโปรเจกต์จริงและ storage branch/backup copies ก่อนใช้ข้อมูลสลิปจริง ต้องลบทุกสำเนาภายใน deadline เดิมของ parent รวมสำเนาใน child branches ไม่ clone production slip data ไป dev โดยไม่มี retention/สิทธิ์ที่ตรวจแล้ว
