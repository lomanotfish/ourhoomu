# Core API module interface — SW-0036 proposal

Revision: OpenAPI `0.3.1-core-proposal` in [openapi.yaml](openapi.yaml). The file is a logical transport contract for local/dev implementation, not evidence of a deployed API. Its 48 operations cover every route in [API contract v0.1](api-contract.md), including the externally gated LINE callback. `x-status: core-approved` means the user approved development of core behavior; it does not assert a handler exists. Other `x-status` values require fail-closed `503 feature_unavailable` until the named proof/credentials and implementation are accepted.

## Principal and session boundary

```ts
type VerifiedPrincipal = Readonly<{
  userId: UUID; sessionId: UUID; issuer: string; subject: string;
  authTime: Instant; expiresAt: Instant;
}>;
type VerifiedActor = Readonly<{ principal: VerifiedPrincipal; houseId: UUID; membershipId: UUID; role: 'owner' | 'member' }>;
interface IssuerAdapter {
  verifyIdToken(input: { provider: 'google' | 'apple'; idToken: string; expectedNonce: string; expectedAudience: string }): Promise<{ issuer: string; subject: string; authTime: Instant }>;
}
interface SessionAuthority {
  exchangeVerifiedClaims(claims: { issuer: string; subject: string; authTime: Instant }, challengeId: UUID): Promise<SessionDTO>;
  rotate(input: { refreshCredential: string; idempotencyKey: IdempotencyKey; bodyHash: Digest }): Promise<SessionDTO>;
  revoke(sessionId: UUID): Promise<void>;
  verifyAccessToken(token: string): Promise<VerifiedPrincipal>;
}
```

Issuer and subject jointly identify the person; neither email nor client-supplied user ID links identities. Challenge is single-use, nonce-bound and short-lived. Issuer signature, audience, expiry and nonce are verified before mapping. Refresh rotation locks one credential family. The handler hashes the exact `RefreshRequest` body and passes the required `Idempotency-Key`; the caller cannot supply an arbitrary hash. An exact retry with the old credential, same idempotency key and body hash within five minutes returns the original rotated pair only while that family is active; concurrent exact calls converge on one result. A different reuse or retry after the window revokes the family and returns opaque 401. Logout/revocation wins even against an exact retry. Store only credential digests and a five-minute encrypted replay result; never log raw tokens. Clients serialize refresh and retain one key across transport retries. Auth bootstrap/exchange/refresh are `x-status` gated pending real provider/native compatibility and runtime evidence, including Apple on device. Neon Managed Auth is a candidate adapter, not asserted to perform Apple exchange. Session credentials are secrets, never logged. No request body or header may choose the actor, role or house membership.

## Transaction operations

All functions take a server-created transaction context with a fresh `VerifiedPrincipal` and request time. The handler resolves live membership and parent house from the database, including for `/payments/{attemptId}`. The context does not expose client SQL/session `SET`; typed routines use fixed role/grants and parameterized queries. Expiry is checked before data projection and inside a mutation transaction. `403` denotes known forbidden action, `404` hides out-of-scope IDs, and `410` is only for a formerly accessible expired resource.

For every house-bound read and mutation, check active membership before child existence or expiry. A removed/inactive member gets hidden 404 regardless of whether the parent or child still exists or has expired; no retained historical DTO is returned to that former member. An active member gets 404 for an out-of-scope child, 403 for a known in-scope action they cannot perform, and 410 only for a child that was accessible to them and expired while they still have live parent access. A house, collection or opaque invitation does not return 410. Any minimal expiry authorization tombstone is capped by the parent retention deadline. Leave/remove returns a scoped membership tombstone (`active=false`, version increment, `removedAt`) only to the in-flight authorized mutation; the client clears house/private caches before further reads. Each OpenAPI operation lists only applicable statuses through `responses` and `x-error-policy`; public auth has no household 403/404/410, while an unusable invitation token always yields the same opaque 404.

```ts
interface CoreTransactions {
  createHouse(tx: Tx, principal: VerifiedPrincipal, input: HouseCreate): Promise<House>;
  acceptInvitation(tx: Tx, principal: VerifiedPrincipal, tokenDigest: Digest, key: IdempotencyKey): Promise<Member>;
  publishBill(tx: Tx, actor: VerifiedActor, billId: UUID, input: PublishRequest, key: IdempotencyKey): Promise<Bill>;
  reservePayment(tx: Tx, actor: VerifiedActor, billId: UUID, input: PaymentCreate, key: IdempotencyKey): Promise<PaymentSummary>;
  confirmCash(tx: Tx, actor: VerifiedActor, attemptId: UUID, expectedVersion: number, key: IdempotencyKey): Promise<PaymentSummary>;
  rejectCash(tx: Tx, actor: VerifiedActor, attemptId: UUID, reason: string, expectedVersion: number, key: IdempotencyKey): Promise<PaymentSummary>;
  transitionChore(tx: Tx, actor: VerifiedActor, choreId: UUID, action: 'complete' | 'reopen', expectedVersion: number, key: IdempotencyKey): Promise<Chore>;
  readSlip(principal: VerifiedPrincipal, attemptId: UUID): Promise<PrivateNoStoreStream>;
}
```

Use one canonical lock order: global replay-floor singleton when required → house → aggregate parent (bill/schedule) → share/attempt/occurrence ordered by UUID → idempotency/confirmation/event/outbox. Never call providers or stream bytes under money locks. Idempotency binds principal, route and body hash, returns the same resource for the same key/body, and rejects key/body mismatch with 409. A lost response cannot create another payment. `expectedVersion` is checked under lock. If the viewer remains authorized, stale 409 `version_conflict` includes the current positive integer `currentVersion`, with no inline resource projection; the client refetches the live viewer projection before retrying. If live authority is absent, the response follows the route's applicable authorization or expiry status policy and discloses no version. DB uniqueness and locks, not in-process mutexes, decide races.

Publish validates exactly 10,000 bps, active same-house participants and active recipient, account ownership/version, integer satang cap 900,000,000,000, and deterministic largest-remainder allocation in one transaction. Recipient share is self-covered without a payment. A bill has a house-local due date; overdue is a badge derived from that date and outstanding balance, not a money state. The bill's full bank destination is projected only to its recipient and payers who owe; everyone else sees masked metadata. `BillListItem` contains aggregate payment totals and masked metadata, never shares or `recipientAccountPrivate`; `Bill` detail applies live viewer projection. Account selector is draft-creator scoped and masked. Payment list and activity expose summaries only; never artifact locators, full bank details, provider raw response or cross-house references.

Transfer reservation is 30 minutes and cash 24 hours, both capped by parent expiry. Cash remains pending until bill creator confirms, including when creator is payer; that self-confirmation writes an explicit audit event. Confirmation checks remaining share under lock and writes immutable credit/event once; no pending amount reduces confirmed debt. Verify lease is 2 minutes, clock tolerance 120 seconds, reconcile cooldown 30 seconds and at most 8 transient retries. Transfer verification and LINE sending are gated: no mock confirmation from HTTP transport status. Replay floor remains monotonic; provider reference precision and late-result UX need provider extension review before transfer credit is enabled.

`PaymentSummary` is a method-discriminated cash/transfer union. Cash begins at `awaiting_confirmation`; transfer begins at `awaiting_upload` and may become `verifying`, `pending_verification` or `needs_attention` without creating credit. Each payment, bill and chore response includes fresh server-derived action flags for the current viewer; handlers recheck authority on mutations. Chore completion status is `pending/completed/cancelled`, while unassigned is a separate assignment state. Dashboard outstanding means the current viewer's confirmed remaining debt, with owed-to-me and pending amounts separate. The three dashboard aggregate satang totals (`outstandingSatang`, `owedToMeSatang`, `pendingSatang`) are exact nonnegative base-10 integer decimal strings matching `^(0|[1-9][0-9]*)$`, with no per-bill or product-wide cap. Compute them with exact numeric/BigInt arithmetic and serialize without a Number cast, rounding or clamping. Individual bill/payment satang amounts retain the bounded integer contract. For example, three legal bills can produce `"1350000000000"` in one dashboard total.

Slip read rechecks active membership, current uploader-or-recipient identity and parent expiry on every request. House owner and bill creator gain no extra access. It streams from private storage through the API with `Cache-Control: private, no-store`; no read URL, redirect or persistent client cache. Upload is a scoped write target for JPEG/PNG/WEBP up to 5 MiB, followed by server validation and immutable finalize. LINE webhook uses raw-body signature verification before JSON parsing, event dedupe and binding checks; its destination and credential policy remain gated.

Household chores use `YYYY-MM-DD` in the house timezone. A manual one-off uses `ChoreCreate`; a recurring `ChoreRule` requires repeat or rotation mode, `anchorDate`, inclusive `startDate`, optional inclusive `endDate`, daily/weekly interval, canonical weekday numbers Sunday=0 through Saturday=6, and an ordered assignee list. Daily uses no weekdays; weekly requires at least one. Repeat requires exactly one assignee; rotation moves by eligible scheduled date from its stable anchor and does not advance on completion or skip a removed member's slot. The server validates `anchorDate <= startDate <= endDate` when an end exists and current membership of assignees. Preview is bounded to 14 days, generation to 30, with a unique schedule/date occurrence; completion/reopen is assignee-only and writes one event/version transition. Invitation lifetime is at most 7 days. Lists default to 20 and cap at 100 with opaque stable cursors. Parent access ends at creation + 365 days UTC minus 24 hours, child access no later than parent; physical deletion and backup/provider-copy evidence remain separate release gates.

An invitation has one logical issuance and stores a token digest. `InvitationIssued` returns the raw token on create; only an exact same-key/body retry within five minutes may return that same token from an encrypted replay result. After that window the key returns 409 instead of minting another token. Revoke returns `InvitationMetadata` without a token. Invalid, expired, consumed and revoked acceptance tokens all return the same opaque 404 `invite_unavailable` before house metadata is resolved; verified principal is still required. The invitation and membership DTOs use house-scoped identifiers, with no global user ID exposed to every house member.

Account deletion remains gated behind its own workflow and external-copy retention proof. `DELETE /v1/me` has no success DTO in this revision and must fail closed with 503 `feature_unavailable`; it must never return a normal `Me` response that implies deletion completed. A later version will type pending, blocked and completed outcomes after their transitions and effects are approved.

## Error and visibility rules

`previewChoreSchedule` returns a `ChoreSchedulePreview` with household timezone and an array of unsaved `{localDate,assigneeMembershipId}` rows, within the 14-calendar-day window beginning at the submitted start date and capped by end date. It returns no persisted occurrence ID, version or expiry and performs no writes. Empty arrays are valid when no rule dates match that window.

Responses use `{data,requestId}` or `{data,nextCursor,requestId}` and `{error:{code,message,fields?},requestId}`. `Error` is a closed union discriminated by `code`: only `version_conflict` has a required positive integer `currentVersion`; every other code omits it. Both variants retain string-valued `fields` for validation details. The version-conflict envelope contains no resource; the client refetches a live projection, subject to fresh authorization. Expected codes include `validation_error` (400), `unauthenticated` (401), `forbidden` (403), `not_found`/`invite_unavailable` (404), `version_conflict`/`idempotency_conflict`/`recipient_account_unavailable`/`insufficient_share` (409), `expired` (410), `rate_limited` (429), and `feature_unavailable` (503). 429 includes `Retry-After`. Neither 409 nor 503 discloses another household's account, transfer reference or provider detail. Payment `pending_verification` and `needs_attention` are explicit states, never a paid badge.

The OpenAPI success response combines the envelope and operation data schema with `allOf`; the composed response closes unknown fields with `unevaluatedProperties: false` at the outer level. The shared envelope and data extension remain open within that composition so `requestId` and `nextCursor` are valid alongside typed `data`.
