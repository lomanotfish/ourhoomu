## Findings

### P1: Expired-session bootstrap now clears a valid refresh session without refreshing

FILE: `ourhoomu-front/src/session/api-session.ts`

LOCATION: 73–81, 99–129.

ISSUE: `readMe()` uses the raw request helper. `bootstrap()` gets the current access token from the authority, but `getAccessToken()` does not refresh expiry; a protected `/v1/me` 401 therefore immediately clears the session. No call to canonical `refreshAfterUnauthorized()` occurs in this bootstrap path.

IMPACT: Opening the app after access-token expiry signs the user out even though the refresh credential is valid. Removing the separate refresh implementation removed refresh behavior rather than connecting bootstrap to canonical single-flight/replay policy.

INDEPENDENT REPRODUCTION: Inline Bun code constructed the actual `createSessionAuthority` and `createApiSession`, with an expired access token and valid refresh token. The synthetic fetcher would return a fresh session for `/v1/auth/refresh` and a successful profile for its rotated bearer. Calling **`api.bootstrap()`** produced `ApiHttpError` status 401, dispatched only `["https://test.invalid/v1/me"]`, and cleared stored credentials. It never requested refresh.

TEST GAP: `src/session/api-session.test.ts:87` is named as a bootstrap single-flight test, but lines 123–126 call `authority.refreshAfterUnauthorized()` three times and never invoke `api.bootstrap()`. The expiry test at line 307 also manually calls the authority first. These passing tests cannot prove bootstrap refresh.

RECOMMENDED_FIX: Use the existing `createApiClient` protected GET transport for `readMe`, with this same canonical authority, or equivalent existing 401-refresh/replay semantics. Preserve caller abort/revision checks. Test the actual bootstrap method directly with expired access, valid refresh, concurrent bootstrap callers and a lost refresh response; verify a single authority flight with stable key/body and a successful protected profile. Do not manually rotate the authority before invoking the method under test.

### P2: UI asynchronous guards retain captured generations and remain incomplete

FILE: `ourhoomu-front/app/api.tsx`

LOCATION: 63–108; 248–259; 346–376.

ISSUE: `authAtStart === authGeneration` compares two values captured from the same render, so it cannot observe a later auth generation. The auth-triggered `load()` effect increments `loadGeneration`, but not `dataGeneration` used by pending house/account reads. Several mutation continuations still lack any generation guard: invitation issuance compares the captured `activeHouse` to its own captured ID; account save calls `setAccounts(await loadAllAccounts(...))` without validating the current session after awaiting.

IMPACT: A delayed previous-session/previous-house response can repopulate state after observable auth/cache invalidation or after switching houses. Exposing the revision in context improves rerendering but does not make those closures current.

RECOMMENDED_FIX: Compare asynchronous results against the live authority revision or a live ref, invalidate all relevant data generations when auth changes, and apply the guard to every authenticated state-setting continuation. Ensure stale 401/error responses also cannot clear a newer identity. Add a focused composition/UI regression for a delayed protected response crossing auth or house change. This finding is source-verified; no browser/native reproduction was executed in this bounded recheck.
