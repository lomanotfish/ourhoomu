- Cloudflare Workers Free มี Cron และ Queues ให้ใช้ได้ แต่ไม่ได้รับประกันความสำเร็จตาม deadline: Cron มี CPU 10 ms/call, queue retention มีเพียง 24 ชั่วโมง และ quota/consumer capacity เป็นตัวคุมงาน. งาน purge จึงต้อง fail closed, ทำเป็น batch ที่เล็กและต่อเนื่อง มี DB-backed retry ledger และ alert/hold เมื่อเริ่มตกกำหนด. Free tier ยังไม่มีหลักฐานว่า purge ได้ครบกับ production volume โดยไม่วัด workload จริง
- Neon Free ณ วันที่ตรวจให้ PostgreSQL 1 GB/project, 100 CU-hours/month, 10 branches, PITR/instant restore 6 ชั่วโมง และ object storage 5 GB/project. Neon ยังไม่ได้ให้หลักฐานเชิงสัญญาในแหล่งที่อ่านว่าการลบราย-record จาก live data ทำลายทุก backup/history/object version ภายใน 365 วัน
- SlipOK เปิดเผยว่าการตั้ง `log:true` ทำให้เก็บข้อมูลสลิป และ FAQ ระบุประวัติการตรวจ/กลุ่ม LINE ของร้านเก็บ “ตลอดไป”. หากใช้ logging mode นี้ R12 พิสูจน์ไม่ได้และขัดกับขีดสูงสุด 365 วัน จึง **ห้ามส่งสลิปจริง/เปิด integration** จนกว่าจะได้หลักฐานลบ/retention เป็นลายลักษณ์อักษรและอนุมัติ scope; ทางเลือกคือใช้โดยไม่เก็บ log หากยืนยันได้ว่าการตั้งค่านี้ครอบคลุมทุก payload/copy และทดสอบผล dedupe/ตรวจซ้ำในระบบเราเอง
- LINE Messaging API เองไม่ได้ให้ retention guarantee สำหรับข้อความ push ที่ OurHoomu ส่งหรือสำเนาบนอุปกรณ์ผู้รับ. ### Feasibility math / worst case

Current domain proposal (not user-approved) schedules purge hourly starting at `expires_at = created_at + 364 days`, leaving 24 hours before `retention_deadline_at = created_at + 365 days`. If hourly job stalls for `k` hours, backlog can accumulate at the arrival rate of expired aggregates. To catch up before hard deadline, measured sustained throughput must exceed new expiry arrivals and drain existing backlog within remaining time. For `N` overdue aggregates, `r` records deleted per aggregate, and `o` stored objects per aggregate, a first-order bound is `ceil(N * (r + o) / B)` calls at batch size `B`, but this ignores index scans, DB transaction/lock time, retries and concurrent writes. At most 24 hourly attempts remain inside the 24h grace window; Cloudflare allows 50 external subrequests per invocation, so the theoretical upper bound is 1,200 calls per aggregate worker/day before shared traffic/quota, CPU and DB calls. That is not a throughput guarantee.

At 24h overdue, the current proposal has no remaining safety margin: the next action must be alert + release/purge incident, preserve fail-closed access, and escalate to the assigned operator/provider. Do not silently extend expiry or weaken 365-day requirement. Test at least 1x and 10x projected backlog plus retries, provider timeout, object-delete partial failure, Worker CPU exhaustion, missed cron, request quota exhaustion, and concurrent payment/upload near expiry. Record p50/p95 items per run, oldest pending age, per-provider delete success, DB lock time, and completion before deadline. If measured capacity cannot sustain `arrivals + backlog drain`, paid Workers or another authorized scheduler/host is a product cost/authorization decision, not an automatic implementation choice.

**Outbox:** do not store payload/sensitive data in queue messages or long-lived logs. Use durable DB outbox as source of truth, atomic enqueue with payment confirmation, unique business key, lease/attempt/next-attempt/deadline fields, bounded exponential backoff, and explicit terminal `needs_attention`. Purge/retry workers must re-check parent expiry and destination binding before send; expired rows are canceled before any external call. Cloudflare queue expiry/DLQ and LINE retry-key 24-hour validity cannot support 365-day retries. Follow existing [LINE design](../../project/line-oa.md); no actual credentials or recipient were supplied.

## Neon Postgres, storage, history and branch copies

**Documented current plan:** Neon announced on 2026-10-02 that Free currently includes 1 GB PostgreSQL storage per project, 100 CU-hours/month, max autoscaling 2 CU, 10 branches, a 6-hour instant restore window, and 5 GB object storage/project. Exact production project plan, actual use/egress, whether quotas changed after capture, backup/history settings, and enterprise/support deletion commitments have not been checked (external resource reads were explicitly out of scope).

**What a row/object delete establishes:** a successful Postgres `DELETE` establishes that the live branch no longer returns the row; private bucket access establishes an access policy, not deletion. Neon describes Postgres copy-on-write branch/history and Object Storage branch lineage/version semantics. Child branches inherit the parent’s data/files at fork time, and child delete is isolated from parent/siblings; object delete may be a tombstone/version marker in that branch. Therefore old branches, PITR snapshots, DB/object history, exports/backups and any copied preview branch are separate retained copies until their own documented purge/lifecycle finishes. The 6-hour PITR setting is a restore capability window, not proof the underlying storage provider immediately physically erases versions at its end.

**Required proposal:** disallow branches containing production PII by default. If production-data branches are necessary for recovery, enumerate branch IDs/owners and expiry; no manual/preview/test branch may outlive the strictest source deadline. Before opening an API after PITR/restore/branch reset, run a global access-expiry filter and deterministic purge sweep against restored state, apply a saved non-rewinding singleton replay floor so a restored DB cannot credit old transfers again, reconcile object metadata to bucket objects, detach/revoke bindings for departed members, and only then enable traffic. Test restore points before/after expiry and before/after deletion; prove no expired item/file is readable or replays payment. Confirm with Neon support/product docs the actual backup/WAL/branch/object-version deletion SLA and object delete semantics, and obtain account-plan retention settings/usage evidence. If no enforceable provider bound at ≤365 days exists, this is a release blocker; isolate/avoid that data category or choose a provider/contract that meets the requirement, subject to user authorization.

## Bounded purge / monitoring / restore proposal (not confirmed)

1. **DB is durable job ledger.** Select expired aggregates in keyset batches ordered by `expires_at,id`; claim with short lease/`SKIP LOCKED`; persist phase `access_closed → objects_deleted → children_deleted → parent_deleted`, attempt count, next retry, last sanitized error, deadline. Child deadline is capped to parent. Index all expiry/dependency scans. Each phase idempotent and re-entrant; do not delete DB object references until storage API confirms deletion or item is marked `needs_attention` and hidden by access gate.
2. **Bound each invocation.** Start conservative (e.g. at most 10 aggregates/run and stop before 6 ms CPU or ~20 external subrequests); these are initial tuning proposals, not measured capacity. Keep object deletion requests isolated/bounded; use cursor/continuation and avoid full-table scans. Do not use HTTP `waitUntil` as scheduler or rely on one invocation to finish unbounded work. Existing DB ledger recovers after runtime/queue loss.
3. **Hourly scheduler scans pending backlog, not only “today’s rows.”** Protect access synchronously at `expires_at`, independently of physical deletion. Reserve last 6 hours of the proposal’s 24-hour grace as incident buffer; alert/hold rollout if oldest not-purged age >12 hours, remaining deadline <12 hours, run fails, high queue age/backlog, database unavailable, provider delete fails, or backlog grows across consecutive runs. Alert threshold is proposal; production owner must define paging target/runbook.
4. **Count proof, not only success logs.** For every run emit non-PII metrics: selected, claimed, access denied, objects deleted/failed, DB children/parents deleted, retries, oldest eligible age, max age to full purge, remaining deadline, CPU ms, subrequests, DB time, Cloudflare daily requests/Queue operations. Dashboard minimum: overdue >0 and oldest age; p95 items/sec; delete error rate; quota headroom. Add synthetic due-soon canary with disposable data on an isolated project and alert if one cycle missed. Keep logs shorter than one year and do not include slip bytes/PII/secrets.
5. **Restore is a quarantine workflow.** Restore to isolated branch/environment with public/API routes disabled. Reconstruct authoritative expiry and non-rewindable payment replay fence; identify all rows where `now >= expires_at`; purge child rows/outbox/bindings and objects first; reconcile object listing vs metadata; run access-denial/no-object/no-replay checks; only then obtain operator approval and route traffic. Never restore a production snapshot directly into serving traffic.
6. **Capacity fallback.** If projected + observed work cannot clear every item before hard deadline on Free, the operator must pause affected feature ingestion/access and hold release; then obtain user authorization to pay for additional Worker capacity/alternative scheduler or migrate to a vendor contract with enforceable purge bound. Do not make a “best effort” >365-day policy or rely on repeated queue enqueue as durable retention plan.
